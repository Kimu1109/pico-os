## なぜ制限があるのか

pico-os は単一スレッドのポーリングループで動いています。Luaのコールバック(`loop(dt)` / `press_start` など)の中に終わらないループがあると、そのままOS全体が固まってしまいます。C++側のコードにはレビューがありますが、Luaスクリプトは書く人を選ばないため、事故を検出する仕組みが入っています。

## 実行時間の上限(命令数ベース)

```lua
while true do end  -- これは無限に回り続けず、一定命令数でエラーとして打ち切られる
```

`pico.*` から見える1回の呼び出し(トップレベルの実行・`setup()`・`loop()`・各種イベントコールバック・HTTPのコールバックなど)ごとに、**Luaバイトコード命令数の上限(暫定 200万命令)**が課されています。上限に達すると実行時エラーとして扱われ、`pico.show_error()` と同じ経路(ログ+メッセージダイアログ)で通知されます。

- 時間(ミリ秒)ではなく**命令数**で数えています。実機の処理速度に依存しない決定的な基準にするためです。
- 数えるのは**Luaのバイトコード実行だけ**です。`pico.sd_read()` のようなC関数の実行中(ファイルI/O待ちなど)は数えられません。「うっかり無限ループを書いてしまった」ケースを検出するためのものなので、正当なC++側の処理を巻き込みません。
- `loop()` が一度この打ち切りエラーを起こすと、以降そのアプリの `loop()` は自動的に呼ばれなくなります(毎フレーム同じエラーダイアログが積まれるのを防ぐため)。

### 既知の限界

自分で `pcall` を使ってエラーを握り潰しながらループを続けるようなコードまでは防げません。

```lua
-- これは打ち切られない: 内側のpcallが打ち切りエラーを毎回捕まえてしまう
while true do
    pcall(function() while true do end end)
end
```

想定しているのは悪意ある攻撃者ではなく「うっかり無限ループを書いてしまった開発者」で、通常の書き方であれば確実に止まります。

## メモリ予算

1つのLuaアプリ(=1つの `LuaEngine`)には、確保できるメモリの総量に上限があります(現在の既定値は200KB)。この上限には Lua state 本体・標準ライブラリ・スクリプトが確保するすべてのテーブルや文字列が含まれます。

- 上限を超えると、Lua標準の「メモリ不足」エラーとして安全に失敗します(OS全体が落ちることはありません)。
- ウィジェット本体(`pico.create()` で作られる実データ)や、画像デコード用のバッファ(`pico.image_load()`)は、この予算には含まれません。それぞれ別枠の上限(ウィジェットは通常のヒープ管理、画像は [画像](../images/) に記載の枚数/バイト数上限)で管理されています。
- テーブルや文字列を大量に確保するようなアプリ(巨大なデータを一括で `pico.sd_read()` する、大きすぎるJSONを組み立てる等)はこの上限に達しやすいので、[SDカードアクセス](../sdcard/) の16KiB上限とあわせて意識してください。

## まとめ: つまずいたときに疑う場所

| 症状 | 疑う仕組み |
|---|---|
| 突然エラーダイアログが出て `loop()` が止まった | 実行時間の上限、またはスクリプト中の通常のバグ |
| `pico.sd_read()` が `nil` を返す | ファイルが大きすぎる(16KiB超)、または権限(`sd_outside_app_dir`) |
| `pico.image_load()` が `nil` を返す | 画像枚数(4枚)/合計サイズ(64KiB)上限、または権限 |
| `pico.http_request()` が `false` を返す | `network` 権限が無い、同時実行数の上限、URLが不正/HTTPS |
| Lua自体のエラー(メモリ不足) | LuaEngineのメモリ予算(200KB)超過 |
